# Auth Hook Contract & Identity Architecture (Phase 2 Preparation)

This document defines the identity token claims contract and delivery plan for Phase 2 (Auth Hook & Custom Claims Alignment).

---

## 1. Identity Token Claims Options

### Option 1: Nested Claims (`app_metadata.tenant_id`, `app_metadata.role`)
* **Structure**:
  ```json
  {
    "aud": "authenticated",
    "role": "authenticated",
    "app_metadata": {
      "tenant_id": "a0000000-0000-0000-0000-000000000001",
      "role": "admin"
    }
  }
  ```
* **Characteristics**:
  * Top-level `claims.role` remains the Postgres DB role (`"authenticated"`).
  * Application tenant identity and user authorization role are stored inside `claims.app_metadata`.
  * Preserves native Supabase GoTrue token convention.

### Option 2: Independent Root Claims (`tenant_id`, `user_role`)
* **Structure**:
  ```json
  {
    "aud": "authenticated",
    "role": "authenticated",
    "tenant_id": "a0000000-0000-0000-0000-000000000001",
    "user_role": "admin"
  }
  ```
* **Characteristics**:
  * Closely aligns with standard Supabase RBAC custom claim examples.
  * Avoids reusing top-level `role`.

---

## 2. Recommendation for Cleanleaf

**Recommendation**: **Option 1 (`app_metadata.tenant_id`, `app_metadata.role`)**.
* **Reasoning**: All existing backend consumers in Cleanleaf (`server/_core/context.ts`, `server/_core/trpc.ts`) and RLS policies (`011_fix_audit_logs_select_rls.sql`, `008`, `009`, `010`) already read from `app_metadata.tenant_id` and `app_metadata.role`. Adopting Option 1 preserves complete backward compatibility without breaking existing application code or RLS policies.

---

## 3. Phase 2 Delivery Unit

The Phase 2 delivery unit MUST be submitted as an atomic, complete package containing:
1. **Auth Hook PL/pgSQL Function**: Injects `app_metadata.tenant_id` and `app_metadata.role` into JWT claims while keeping `claims.role` as `"authenticated"`.
2. **Helper Functions**: Alignment of `public.get_current_tenant_id()` and `public.get_current_role()` to read `app_metadata`.
3. **RLS Policies**: Audit of all policies using tenant and role context.
4. **Automated Verification Suite**: Full pgTAP and integration test coverage.

---

## 4. Staging Validation Walkthrough

When Phase 2 is ready for staging verification, follow these steps:
1. **Login & Obtain Real JWT Token**: Authenticate as a tenant user against the staging GoTrue endpoint.
2. **Decode Token Locally**: Use `jwtpeek` or `jwt-decode-cli` locally to verify token structure:
   * Verify top-level `role` is `"authenticated"`.
   * Verify `app_metadata.tenant_id` matches user's tenant UUID.
   * Verify `app_metadata.role` matches user's application role (`admin`, `owner`, `user`, or `super_admin`).
3. **Execute Authorized Action**: Issue a tRPC procedure mutation (e.g. `createAnalysis` or `updatePlan`).
4. **Verify Audit Record**: Confirm that `audit_logs` contains a new row generated by `service_role` writer.
5. **Attempt Direct Unauthorized Insert**: Issue a direct SQL or REST `INSERT INTO audit_logs` with the user token and confirm `42501 permission denied`.
6. **Verify Cross-Tenant RLS Isolation**: Authenticate as Tenant B and verify that Tenant A's audit logs are completely invisible.
